**版本**：v1.0（初赛提交稿）　**日期**：2026-10

## 一、作品概述

### 1.1 行业与技术背景

随着人工智能技术从单模型能力向系统化协作演进，异构智能体之间的互联互通成为规模化落地的核心瓶颈。2026 年 5 月 22 日，GB/Z 185《人工智能 智能体互联》（Agent Interconnection Protocol，AIP）国家标准系列正式发布，首次为异构 AI 系统互通、多智能体协同交互划定了统一技术规范，覆盖总体架构、身份码、身份管理、智能体描述、发现、交互与工具调用七大部分，为"AI+行业"的标准化落地提供了底座。

然而当前产业落地仍普遍面临四类痛点：

1. **协议割裂**：各厂商智能体采用私有协议，互调成本高、难以形成生态；
2. **身份与信任缺失**：缺乏统一的智能体身份码（AIC）与双向认证机制，安全交互无从谈起；
3. **发现机制薄弱**：缺少标准化的能力描述（ACS）与发现服务（ADP），智能体"找到彼此"依赖人工配置；
4. **标准落地实践人才紧缺**：国标发布后，高校与产业界均缺乏可运行的工程化参考。

本作品面向上述痛点，基于 AIP 国家标准与 ACPs 开源参考实现，二次开发一套**多智能体协同软件开发系统**，并在梧桐智能体互联平台完成注册、发现、互联、访问全流程验证，探索"国标 + 开源 + 行业场景"的标准化落地路径。

### 1.2 作品目标定位

**核心研发目标**：基于开源代码、遵循 AIP 标准，搭建一套可运行、可验证、可推广的多智能体协同软件开发系统：

- **业务目标**：将软件开发任务按"需求分析 → 架构设计 → 代码审查/测试设计 → 文档生成"全流程拆解，由五个专职 Partner 智能体协同完成，输出可落地的工程交付物；
- **技术目标**：
  - 完成智能体能力描述（ACS）规范编写与可信注册（ATR），取得智能体身份码（AIC）与身份证书（CAI）；
  - 接入梧桐智能体互联平台，完成**注册 → 自动发现 → 跨端互联访问**全流程验证；
  - 建立 Direct RPC 与 Group AMQP 双通道通信，实现 mTLS 双向认证；
  - 通过 AMP 心跳上报维持存活状态，留存后台访问数据；
  - 在开源代码基础上完成**场景插件化、存活感知路由、双通道容错执行**三项深度二次开发；
- **效益目标**：为软件工程领域提供"多智能体协同研发"的标准化参考范式，验证 AIP 国标在行业场景中的可组合性，预期可向教育、中小软件企业、开源社区推广。

**硬性验证要求**：在梧桐智能体科研平台（https://wt.ioa.pub/）完成智能体注册、自动发现、跨端互联访问全流程验证，并留存平台后台访问数据（详见第五章）。

## 二、需求分析

### 2.1 行业痛点剖析

围绕"异构智能体互通"与"多智能体协同落地"，本作品需解决以下关键技术问题：

| 痛点 | 具体表现 | 本作品应对 |
|------|---------|-----------|
| 协议不统一 | 智能体间调用无标准消息模型，任务状态（accept/working/complete…）各写各的 | 采用 AIP 标准 TaskCommand/TaskResult 对象与状态机 |
| 身份可信缺失 | 无统一 AIC 与证书体系，无法做 mTLS 双向认证 | 通过 ATR 注册取得 AIC/CAI，全链路 mTLS |
| 能力发现困难 | 智能体能力靠人工录入，无法动态匹配 | 编写标准 ACS，经 ADP 发现服务动态检索 |
| 平台适配成本高 | 每家平台一套接入协议，迁移成本大 | 严格对齐 AIP 国标 + 梧桐平台，一次适配多场景复用 |
| 协同可靠性差 | Partner 离线即任务失败，无自愈能力 | 自研存活感知路由 + 双通道容错执行 |

### 2.2 场景与功能需求调研

**目标场景**：软件开发团队的多角色协同。软件开发天然具有"多角色、强分工、流程化"特征——需求、架构、编码、测试、文档由不同角色负责，且产出物环环相扣，非常适合作为多智能体协同的验证场景。

通过文献调研、行业案例分析与平台适配测试，梳理出以下功能需求：

- **多智能体协同**：Leader 接收用户需求，拆解为五维任务并分发到专职 Partner；Partner 独立完成子任务并回报状态与产出；
- **安全交互**：智能体间 mTLS 双向认证，任务消息防篡改、防冒充；
- **任务全生命周期管理**：start → accepted → working → awaiting-input → awaiting-completion → completed，支持中途补充输入、拒绝超范围请求、取消任务；
- **远程调度**：Leader 与 Partner 可部署在不同服务器，通过公网端点与消息队列通信；
- **存活与可观测**：心跳上报、访问日志、指标采集，供平台监控与访问量统计。

**四类指标**：

| 类别 | 指标 | 目标值 |
|------|------|--------|
| 功能 | 智能体注册/发现/互联/访问全流程 | 全部通过 |
| 性能 | 单次任务下发到产出（RPC） | < 30 s（LLM 推理主导） |
| 兼容 | AIP 02.02 协议、梧桐平台、主流 LLM API | 全部兼容 |
| 部署 | 一键脚本部署、容器化可选 | 1 条命令拉起全栈 |

### 3.1 基础开发资源选型

| 资源 | 选型 | 说明 |
|------|------|------|

**对 AIP 国标的遵循思路**：逐项对齐国标七大部分——总体架构（Leader/Partner 分层）、身份码（AIC 申请与携带）、身份管理（ATR 注册 + CAI 证书）、智能体描述（ACS 编写）、发现（ADP 查询）、交互（AIP 消息模型与状态机）、工具调用（skills 能力声明），确保作品是"国标原生"而非私有协议。

### 3.2 核心技术方案设计

#### 3.2.1 整体架构设计

系统采用**三层分层互联架构**：

```text
┌─ 用户层 ────────────────┐
│  Web UI(:9030) / API(:9031)│
└──────────┬──────────────┘
┌─ 编排层（Leader） ───────┐
│ 意图识别 → 规划 → 存活感知路由 │
│ → 双通道执行 → 完成闸门 → 聚合  │
└──────────┬──────────────┘
┌─ 能力层（Partner ×5） ───┐
│ 需求分析(9021) 架构设计(9022)  │
│ 代码审查(9023) 测试设计(9024)  │
│ 文档生成(9025)                │
└──────────┬──────────────┘
┌─ 平台层（梧桐 wt.ioa.pub）─┐
│ Registry / CA / Discovery /  │
│ MQ(5671) / Monitor / Kafka(19092) │
└─────────────────────────┘
```

**协议适配层**：Leader/Partner 均通过 `acps_sdk` 实现 AIP 消息模型（TaskCommand/TaskResult/Product/DataItem）、JSON-RPC 封装、AMQP 群组封装与 mTLS 身份绑定，业务代码与协议解耦。

**平台通信交互模块**：
- 注册面：`acps-cli`（auth login → agent save → agent submit → agent check → cert eab fetch → cert issue）；
- 发现面：Leader 经 `DiscoveryClient` 调用 ADP `/discover`，按维度查询 Partner；
- 通信面：Direct RPC（HTTPS/JSON-RPC）+ Group（AMQP 群组会话）双通道；
- 观测面：AMP 心跳/访问/指标 Emitter 实时上报。

#### 3.2.2 关键技术选型

| 技术点 | 选型方案 |
|--------|---------|
| 注册发现 | ATR 可信注册（ACS 审核 → AIC）＋ ADP 发现查询 |

### 4.2 关键技术落地实现

#### 4.2.1 场景插件化改造（自主开发）

官方 demo 的场景通过 `scenario/expert/<id>/` 目录声明，运行时由 `ScenarioLoader` 自动发现。本作品将官方"旅游"场景整体替换为"软件开发"场景：

**domain.toml（节选）**：定义五个业务维度与静态映射

```toml
[meta]
id = "dev"
name = "软件开发助手"

[dimensions.requirement]
name = "需求分析"
description = "软件需求分析与规格说明。包括需求澄清、功能/非功能需求梳理、用例编写、验收标准定义。"

[dimensions.code_review]
name = "代码审查"
description = "代码质量审查。包括规范检查、缺陷识别、性能瓶颈、安全漏洞与重构建议。"

[partners.static_mapping]

```

**prompts.toml**：覆盖 LLM-2（规划器）与 LLM-6（聚合器），注入软件开发领域的规划规则（维度优先级：需求 > 架构 > 审查/测试并行 > 文档）、instructionData 诚实原则（用户未给出的技术栈不得臆造），并定制工程交付物输出格式。

#### 4.2.2 创新模块一：存活感知路由

**问题**：官方 demo 的规划器按静态映射/技能匹配选 Partner，不感知对方存活状态。真实平台中 Partner 心跳超时（>90s）即判离线，任务下发到离线 Partner 将产生不可控超时。

**方案**：新增 `HealthAwareSelector` 模块，在编排执行前基于 AMP/Discovery 返回的存活状态（aliveMap）对规划结果做健康过滤——在线 Partner 正常派发，全部离线维度标记 fallback 由 Leader 兜底提示。

```python
class HealthAwareSelector:
    def filter_dimension(self, dimension_id, partners):
        online, offline = [], []
        for p in partners:
            if self.is_alive(p.get("partnerAic") or p.get("aic", "")):
                online.append(p)
            else:
                offline.append(p)          # 心跳离线 → 跳过
        if online:
            return HealthRoutingDecision(..., status="active")
        return HealthRoutingDecision(..., status="fallback")  # 全离线 → 兜底
```

**验证**：`scripts/health_route_demo.py` 离线演示（无需平台/LLM），实测 5 维度中 1 维度离线时路由正确降级（输出见附录 A）。

#### 4.2.3 创新模块二：双通道容错执行

**问题**：AIP 定义 Direct RPC 与 Group 两种交互模式，官方按 ACS 能力位静态选择一种。单通道在瞬时故障（连接失败/TLS 握手失败/超时）下无自愈能力。

**方案**：新增 `DualChannelExecutor`，将两种模式封装为主备关系——RPC 失败自动降级到 Group AMQP，利用 MQ 可靠性重试；两通道均失败返回结构化失败信息供编排层决策。

```python
class DualChannelExecutor:
    async def run(self, partner, instruction):
        # 主通道 Direct RPC
        try:
            return await asyncio.wait_for(self._rpc_fn(partner, instruction),
                                          timeout=self._rpc_timeout)   # → rpc
        except (TimeoutError, Exception):
            # 备通道 Group AMQP
            return await self._group_fn(partner, instruction)           # → group
```

**验证**：离线演示实测 RPC 失败毫秒级自动降级（输出见附录 A）。

#### 4.2.4 梧桐平台接入全流程（ATR）

按 `acps-cli` 官方流程完成 6 个智能体（1 Leader + 5 Partner）的可信注册：

```bash
# ① 登录（梧桐平台账号）
acps-cli auth login --username <账号> --password '<密码>'
# ② 保存 ACS 草稿（aic 留空串 ""，由平台审批分配）
acps-cli agent save --acs-file <agent>/acs.json --json
# ③ 提交审核
acps-cli agent submit --agent-id <AGENT_UUID> --json
# ④ 审核通过后同步 ACS 确认 AIC
acps-cli agent check --acs-file <agent>/acs.json --json
# ⑤ 获取 EAB 并签发 mTLS 证书（clientAuth）
acps-cli cert eab fetch --aic <AIC> --output private/eab.json --json
acps-cli cert issue --aic <AIC> --eab-file private/eab.json --usage clientAuth
# ⑥ 证书放入对应目录（leader/atr/、partners/online/<name>/）
```

**实施要点**（依据平台答疑确认）：
- `aic` 注册时留空字符串，审批时由注册服务分配并写回，`endPoints` 中 `{AIC}` 占位符同步替换；
- 平台允许直接注册实体智能体，不强制先注册本体；
- 平台不提供域名，智能体须部署在公网可达端点（本作品使用云服务器公网 IP + 独立端口 9021-9025/9031）；
- MQ 服务端已信任 Agent CA Root 签发的 clientAuth 证书，直连 wt.ioa.pub:5671；
- AMP 心跳通过 Kafka（wt.ioa.pub:19092）直连上报，无需鉴权；心跳须定时上报维持存活（静默 >90s 判失效）；
- 审核通过到可被 Discovery 检索约 10 分钟。

#### 4.2.5 核心交互时序

```text
用户 ──HTTP──▶ Leader(L-1 意图识别)
              │  TASK_INPUT: "帮我设计一个图书管理系统的方案"
              ├─▶ LLM-2 规划: 拆解 requirement/architecture 两维
              ├─▶ 存活感知路由: 校验两个 Partner 在线
              ├─▶ RPC start ──▶ 需求分析师(9021)
              │     ◀── awaiting-completion + 需求规格 ──┘
              ├─▶ RPC start ──▶ 架构设计师(9022)
              │     ◀── awaiting-completion + 架构方案 ──┘
              ├─▶ 完成闸门: complete 两个任务
              ├─▶ LLM-5 一致性校验 → LLM-6 聚合
              ◀── HTTP 返回完整工程交付方案
```

#### 4.2.6 开发中遇到的兼容性问题与优化

| 问题 | 现象 | 解决方案 |
|------|------|---------|
| 证书链不匹配 | 客户端证书 issuer 与 MQ 信任锚不一致，TLSV1_ALERT_UNKNOWN_CA | 按平台答疑确认双根信任包，等待平台刷新后直连；统一使用 Agent CA Root 签发路径 |
| 心跳存活判定 | Discovery 查不到智能体 | 配置 AMP 心跳定时上报（Kafka 直连），静默 >90s 判失效，持续心跳维持存活 |
| 场景残留 | 官方旅游场景 JSON/partner 目录混入 | 全量删除替换，ACs/skills 全部重写，避免评审误判"仅复用示例" |
| LLM 输出漂移 | 规划器 JSON 输出不稳定 | instructionData 诚实原则硬规则 + JSON 输出格式严格约束 + 温度调低 |

## 五、应用成效

### 5.1 功能成果展示

系统全部功能逐一验证通过：

1. **智能体注册**：6 个智能体（1 Leader + 5 Partner）完成 ATR 注册并通过平台审核，取得 AIC 与 mTLS 证书；
2. **自动发现**：Leader 通过 ADP 查询可稳定发现 5 个 Partner 及其技能（skills）；
3. **跨端互联访问**：Leader 通过 Direct RPC 调用 Partner 完成任务下发与产出回收；群组模式经 MQ 验证可用；
4. **多智能体协同**：以"图书管理系统方案设计"为例，需求分析师产出需求规格 → 架构设计师产出架构方案 → Leader 一致性校验并聚合为完整交付方案（演示记录见附录）；
5. **存活与观测**：AMP 心跳持续上报，平台可查询存活状态；访问日志实时生成。

## 六、总结与展望

### 6.1 经验总结

**成功经验**：
1. **标准先行**：先吃透 AIP 国标与官方教程的最小模型（状态机、数据对象、注册流程），再进入复杂 demo 改造，避免了"黑盒式"复制；
2. **分层解耦**：将场景（domain/prompts）、通信（SDK）、编排（core）分层，场景替换不动核心代码，改造风险可控；
3. **创新独立成模块**：存活感知路由、双通道容错作为独立可插拔模块实现，可通过离线演示独立验证，答辩证据充分；
4. **平台优先**：把梧桐平台接入（注册/审核/证书/心跳）作为关键路径前置推进，为联调留足缓冲。

**不足之处**：
1. 场景数据依赖 LLM 生成能力，复杂软件开发任务的产出质量受模型能力上限约束；
2. 双通道降级目前为"顺序重试"策略，未实现并发探测（RPC 与 Group 同时发、先到先得）；
3. 访问量等平台侧数据需在部署上线后持续积累，本稿提交时以流程验证为主。

### 6.2 未来规划

1. **功能拓展**：增加多轮需求澄清的对话式交互、代码文件级上下文注入、Partner 技能热更新；
2. **调度增强**：基于访问频次与历史成功率实现智能负载均衡，双通道升级为并发竞速模式；
3. **场景扩展**：将场景插件扩展到运维排障、教学辅导、科研协研等方向，输出场景开发模板；
4. **生态共建**：在梧桐平台发布智能体与技能，在 AIP 开源社区贡献接入实践与文档，推动国标落地。
